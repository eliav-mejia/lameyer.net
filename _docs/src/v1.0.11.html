1Resumen

1.0.10 dejó todo el sitio en español y vinculó la divisa a la bandera (España → EUR, México → MXN). 1.0.11 aplica la misma bandera a /pages/terminos/: el índice muestra una lista de cláusulas por región, con pestañas España y México. La pestaña España contiene la política estándar española de comercio electrónico para productos electrónicos; la pestaña México, las cláusulas de la Ley Federal de Protección al Consumidor (LFPC).

Además se documentan dos opciones para traducir el sitio y gestionar su contenido como un CMS headless, ambas pendientes de decisión: A Vite + react-i18next (un namespace por página, carga diferida) y B Next.js + next-intl con generación estática y rutas /es/…. Las dos usan un TMS de plan gratuito (Tolgee o Crowdin) y DeepL para pre-rellenar. El único código nuevo de esta parte es tools/i18n/deepl-prefill.mjs, que funciona con cualquiera de las dos.

Revisión legal. Las cláusulas de México y la sección RAEE de España son un borrador redactado a partir de la normativa citada. Deben revisarlas un abogado antes de publicar, igual que los marcadores […] del vendedor (incluido el nuevo [Nº de registro RII-AEE]).

3Términos por región (hecho)

3.1 Cómo funciona

pages/terminos/index.html

const region = useLocale().country;            // 'ES' o 'MX', la bandera de la cabecera
const sections = sectionsFor(region);          // filtra SECTIONS por `regions` y numera 01, 02…
CLAUSES.garantia  = { ES: GarantiaES, MX: GarantiaMX }   // cláusula distinta por región
CLAUSES.vendedor  = Vendedor                             // cláusula común (recibe `region`)
  • Pestañas = bandera. Pulsar «México» en el índice llama a chooseLocale(): cambia también la bandera de la cabecera y la divisa de la tienda. Abrir los términos con la bandera de México muestra directamente la pestaña México.
  • Mismos anclajes. Los ids (#devoluciones, #garantia, #envios, #precios) existen en ambas regiones, así que los enlaces de las fichas de producto y del carrito siguen funcionando. Al cargar, la página baja al anclaje cuando la cláusula ya está renderizada.
  • Accesibilidad. role="tablist" / tab / tabpanel y aria-selected.

4Opción A — Vite + react-i18next pendiente

Mantiene el sitio como SPA de React, pero con un paso de build: Vite compila el JSX (adiós a Babel en el navegador) y react-i18next carga los textos por página.

4.1 Estructura

locales/
  es/ common.json  inicio.json  tienda.json  terminos.json  blog.json  blog-security-rate-limiting.json …
  en/ …                                   // relleno por DeepL, revisado en el TMS
src/i18n.ts
  • Un namespace por página (terminos, tienda, un namespace por artículo del blog) más common para cabecera, pie, cookies y acceso.
  • Carga diferida: cada namespace es un import() dinámico; Vite lo convierte en un chunk propio que solo se descarga en la página que lo usa.
  • Los términos por región se modelan como claves dentro del namespace: terminos:es.garantia.p1, terminos:mx.garantia.p1.

src/i18n.ts

import i18n from 'i18next';
import { initReactI18next } from 'react-i18next';
import resourcesToBackend from 'i18next-resources-to-backend';

i18n.use(initReactI18next)
    .use(resourcesToBackend((lng, ns) => import(`../locales/${lng}/${ns}.json`)))   // un chunk por namespace
    .init({ lng: 'es', fallbackLng: 'es', ns: ['common'], defaultNS: 'common',
            interpolation: { escapeValue: false }, react: { useSuspense: true } });

// en cada página: const { t } = useTranslation('terminos');  t('es.garantia.p1')

4.2 Límites

  • Sigue siendo renderizado en cliente: el HTML inicial sigue vacío para los rastreadores (ver el artículo «SSR y generación estática» del blog). Se puede prerenderizar con vite-plugin-ssr/vike, pero eso ya se acerca a la opción B.
  • Las URLs no cambian de idioma; un segundo idioma necesitaría ?lng= o rutas propias y hreflang a mano.
  • Esfuerzo estimado: extraer ~1.500–2.000 cadenas a JSON y cambiar cada texto por t(); migración página a página posible.

5Opción B — Next.js + next-intl + generación estática + /es/ pendiente

Pasa a Next.js (App Router) con exportación estática: cada página se genera en build como HTML completo bajo un prefijo de idioma, lo que además resuelve el HTML vacío del sitio actual.

app/[locale]/layout.tsx                       // NextIntlClientProvider, <html lang={locale}>
app/[locale]/pages/terminos/page.tsx          // /es/pages/terminos/
app/[locale]/blog/[series]/[slug]/page.tsx    // /es/blog/security/rate-limiting/
i18n/routing.ts   i18n/request.ts   messages/es/*.json

i18n/routing.ts · next.config.mjs

export const routing = defineRouting({ locales: ['es'], defaultLocale: 'es', localePrefix: 'always' });   // 'en' cuando se traduzca

// en cada page.tsx / layout.tsx
export function generateStaticParams() { return routing.locales.map(locale => ({ locale })); }
setRequestLocale(locale);                                  // habilita el renderizado estático

// next.config.mjs
export default withNextIntl({ output: 'export', trailingSlash: true, images: { unoptimized: true } });
  • Mensajes por página: un archivo por namespace en messages/es/, combinados en i18n/request.ts; cada página solo pasa al cliente los namespaces que usa.
  • Exportación estática sin middleware: con output: 'export' el middleware de next-intl no se ejecuta, así que / necesita una página que redirija a /es/. Las URLs actuales (/pages/…, /blog/…) deben redirigir a /es/…: reglas de redirección de Cloudflare (301 reales) o la lista moved de 404.html.
  • SEO: <link rel="alternate" hreflang> y canónicas por idioma generadas desde routing; sitemap generado en build.
  • Región ≠ idioma: España y México comparten /es/; la bandera sigue guardándose en el navegador (o en una cookie) y elige divisa y cláusulas. Rutas /es-mx/ solo si algún día cambia el texto, no solo la divisa.
  • Esfuerzo estimado: mayor que A (reescritura a componentes de Next, datos del blog y de la tienda en build), pero entrega HTML estático rastreable.

6.2 Flujo propuesto

  1. Se escribe o edita el texto en español (locales/es/<página>.json) en un pull request.
  2. node tools/i18n/deepl-prefill.mjs --target en rellena solo las claves que faltan y las anota en locales/en/_prefill.json.
  3. El TMS importa las traducciones como sin revisar; una persona las corrige y aprueba.
  4. El TMS devuelve los JSON aprobados al repositorio (pull request de Crowdin o tolgee pull) y el build los publica.

6.3 tools/i18n/deepl-prefill.mjs

  • Solo rellena claves vacías o ausentes; nunca sobrescribe una traducción revisada. Mantiene el orden de claves del archivo fuente.
  • Protege {{name}} (react-i18next), {name} (next-intl / ICU) y los términos de marca (Lameyer, MC-SE, Modular Core, Serverless Edge, más --keep) con etiquetas <x> que DeepL no traduce.
  • --dry-run cuenta claves y caracteres sin llamar a la API; útil para no pasar del plan gratuito de DeepL API (500.000 caracteres al mes). Clave :fx → endpoint gratuito automáticamente.
  • Probado contra un servidor DeepL simulado: placeholders y marcas intactos, claves existentes conservadas, segunda ejecución sin cambios.
