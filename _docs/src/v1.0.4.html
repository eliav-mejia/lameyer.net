Release 1.0.4 — Product pages + simulated database

The shop moves from inline arrays to a JSON “database”, gains a page per product, and shares one cart across every page. Status: staging / pre-launch.

1Summary

1.0.3 left a data layer in the folder that nothing loaded (1.0.3 §5.5). 1.0.4 makes it the only source: the shop and the new product pages read public/db/categorias.json and public/db/productos.json through one loader in js/tienda.jsx. The inline PRODUCTS, CATEGORIES and IMAGE_CREDITS are gone; image credits now live in each product's image object. Each of the 30 products gets its own URL, /pages/components/<slug>/, generated by a Python script. The cart, product card and cart drawer move into tienda.jsx so the shop and every product page share them.

Staging. Prices, stock, specs and descriptions are sample data for the MVP pre-launch manual input test. Seller details (SELLER.name, nif, address) and both return addresses are still […] placeholders, and these are shown on the terms page.

3How it works

3.1 Data layer

js/tienda.jsx · lines 105–145

const DB_BASE = '/public/db';
const loadJson = (name) =>
    fetch(`${DB_BASE}/${name}.json`, { cache: 'no-cache' })   // revalidate so manual edits show up at once
        .then(r => (r.ok ? r.json() : Promise.reject(new Error(`${name}.json: HTTP ${r.status}`))));

db.catalog()   // { categories (sorted by sort_order), products (active !== false) }, fetched once per page
useCatalog()   // { status: 'loading' | 'ready' | 'error', categories, products, byId, bySlug, category }
  • One seam for a real database. Only loadJson / db.catalog() touch storage. Moving to Supabase, D1 or an API means replacing them and keeping the field names.
  • Loading and error states. CatalogStatus shows three skeleton cards while loading and a “No se pudo cargar el catálogo” panel with a WhatsApp button on error.
  • Inactive products (active: false) are dropped at load, so they vanish from the grid, cart and related items, and their page shows “Producto no encontrado”.

3.3 Product pages

tools/generar-paginas-producto.py · js/tienda.jsx lines 435–651

The generator writes one static shell per active product. The shell contains only what crawlers and link previews need without JavaScript: <title>, meta description (description + price + “Devolución en 30 días”, max 300 chars), canonical URL, Open Graph tags with the 800 px photo, and a <noscript> heading. Then it calls renderProduct(), which finds the product by the last URL segment (slugFromUrl()) and renders:

  • photo with credit, grade badge, stock status, price in the selected currency (EUR plus USD, MXN, GBP, ILS at ECB rates via Frankfurter, with fixed fallbacks);
  • quantity selector (1 to stock, max 99), Añadir al carrito and Comprar ahora (adds and opens the cart);
  • specs table with SKU, full compatible_models list, a WhatsApp “is it compatible?” link with the SKU prefilled, and a “notify me” link when out of stock;
  • up to three related products from the same category, and links to returns, guarantee and shipping in the terms;
  • schema.org Product / Offer JSON-LD (price, currency, availability, condition), injected client-side.

The script refuses to run on duplicate slugs and lists folders that no longer match an active product; it never deletes them. Price, stock and spec edits need no regeneration because pages read the JSON at load; slug, name, compat, description or image changes do.

3.4 Shop page

Category chips keep the selection in ?cat=<id>. Search matches name, compat, every compatible model and the SKU. Each card links to its product page, and out-of-stock cards show “Agotado” with the button disabled. The first three cards load eagerly (unchanged from 1.0.3).

3.5 Cart and order

js/tienda.jsx · lines 161–188, 265–400

  • Storage: localStorage['lm-cart'] = { productId: qty }, via a store wrapper that never throws (private mode, blocked storage).
  • Cross-tab sync: a storage listener updates the cart when another tab changes it, e.g. a product page in one tab and the shop in another.
  • Stale ids: lines whose product is missing or inactive are dropped once the catalogue loads.
  • Checkout: name, delivery (home delivery needs a 5-digit postcode; pickup in Madrid does not) and acceptance of the terms. The order is sent as a prefilled WhatsApp message to SELLER.whatsapp:

4Manual input test: adding or editing a product

  1. Copy a product object in productos.json; give it a new id, slug and sku. Keep the JSON valid and update updated_at.
  2. Add img/productos/<id>-400.webp and -800.webp with credit fields, or set "image": null.
  3. Run python tools/generar-paginas-producto.py from the repo root (or copy a product folder and edit its head by hand).
  4. Check the shop grid, search, the product page, the cart and the WhatsApp message, then commit and push.

5Known issues and limits

  • 5.1 Cart ignores stock. useCart.add and setQty cap at 99, not at product.stock. The product page limits one add to the stock, but adding twice, pressing “Añadir otro” on a card, or pressing + in the cart goes past it. A product that drops to 0 stock also stays in existing carts and can still be ordered.
  • 5.2 Structured data is client-side only. The Product JSON-LD exists only after React renders. Google executes JavaScript, but other crawlers and link-preview bots see only the static head (title, description, OG tags).
  • 5.3 Generated heads can go stale. Name, description and price in each shell's head are copied at generation time. A price edit shows correctly on the page but the meta description keeps the old price until the script is run again.
  • 5.4 No data validation. Nothing checks that category_id exists, that grade is estandar or premium, that prices are numbers, or that image files exist. A broken JSON file takes down the whole shop (error state), not just one product.
  • 5.5 Public sample data. /public/db/ is served publicly by design (README warns against private data). Staging pages are live under the production domain and indexable, with sample prices and placeholder seller data.
  • 5.6 Rates on every load. Each page requests Frankfurter rates; nothing is cached beyond the browser's HTTP cache.
5.7 Legal placeholders. The terms page renders [Razón social], [NIF / CIF], [Domicilio fiscal completo] and two return addresses with [Calle y número]. Spanish e-commerce law (LSSI-CE) requires the seller's identity, tax ID and address. This blocks launch, not staging.
